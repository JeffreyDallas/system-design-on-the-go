Designing a Large-Scale Web Crawler for Language Model Training

Two engineers discuss building an efficient, fault-tolerant web crawler that starts from seed URLs, extracts HTML text for training large language models, and balances coverage, freshness, and resource constraints. They co-design a prioritization and politeness-aware BFS crawler architecture with multi-stage pipeline processing, hybrid storage, and compliance mechanisms.

Design challenge: Design a web crawler that starts from seed URLs and efficiently traverses the web to extract text data for training language models, balancing breadth of coverage, freshness, and resource constraints.

Engineer A

Let's kick off by outlining the key design pillars for the crawler. We need to start from a set of seed URLs, crawl HTML pages, extract text for language model training, and importantly, balance wide coverage, freshness, and resource use. Also, scaling to about one billion pages per month is our immediate target, with room to expand to 10 billion later. What do you think are the most crucial architectural choices to support this?

Engineer B

Given the scale and the freshness requirement, managing the URL frontier efficiently is paramount. A breadth-first search traversal sounds preferable over depth-first — breadth-first helps spread the crawl across diverse hosts and better compliance with politeness, avoiding hammering a single domain. This approach better aligns with fairness and freshness goals because updates can be discovered across many domains rather than deep diving into one.

Engineer A

Agreed. BFS also aids in maintaining a layered URL queue, which can integrate URL priority signals for importance and update frequency. Politeness is another major concern. To prevent overloading any host, we should segment the frontier per host. Each host can have its FIFO queue, and worker threads assigned per host queue will enforce concurrency limits and crawl delays. This helps respect politeness fairly and aligns with observed best practices.

Engineer B

Right, and about prioritization: we need more than pure FIFO. We could assign scores based on factors like PageRank, traffic estimates, or historical change frequency to prioritize recrawling important or frequently updated pages. The frontier would maintain front queues ordered by priority, and back queues enforce host-based politeness, effectively decoupling these concerns, which should improve freshness and relevance in crawled data.

Engineer A

That makes sense. One complexity there is how to compute and update these priority scores at scale without excessive overhead. We’ll likely need a process that periodically recalculates priorities asynchronously. For initial implementation, perhaps we bootstrap with static signals like inbound link counts or seed-based topical relevance, then refine over time with feedback from crawl results.

Engineer B

Another consideration is duplicate detection, both on URL level and content level. For URLs, large-scale Bloom filters can efficiently track seen URLs with low memory, though we must accept some false positives and complement that with a persistent backing store for exact checks. For content deduplication, hashing page contents to detect near-duplicates prevents excess storage. We should store only canonical pages for each duplicate group to save petabytes of storage over time.

Engineer A

Exactly. Storage is another big piece. For five years and upward of petabytes, a hybrid memory and disk solution works best. The URL frontier needs some in-memory caching but fallback to disk-based or cloud-based queues for durability and scale. The fetched HTML and extracted text should go into scalable blob storage like S3, enabling distributed workers to upload asynchronously. Plus, separating the pipeline stages — fetching, parsing/extraction, and storage — improves fault tolerance and allows updates to text extraction independently without re-fetching.

Engineer B

Splitting into a multi-stage pipeline also handles failures gracefully. For example, if parsing fails for some pages, only that stage needs retries. The URL queue in front can use systems such as Kafka or AWS SQS. Kafka provides immutable logs and fine-grained consumer offsets, great for progress tracking and replaying. SQS brings built-in message visibility timeouts and dead-letter queues, easing retry management. We might choose based on operational expertise or cloud ecosystem constraints.

Engineer A

Yes, and regarding politeness enforcement, the crawler workers must respect robots.txt and any crawl-delay directives, though not all sites honor or publish delay values. We should support RFC 9309 robots exclusion rules as a minimum and implement our own politeness delays to avoid inadvertently overloading servers. This also helps with legal and compliance considerations.

Engineer B

Good point. On failure modes, one challenge is unresponsive or slow hosts causing crawler stalls. We should implement timeouts and backoff strategies per host, marking persistently failing hosts offline temporarily. Coupled with dead-letter queues for URLs failing after max attempts, we can avoid indefinite retries and stuck states. It's also critical to prevent infinite loops by having robust URL normalization and seen-set checks.

Engineer A

Definitely. Another failure to watch for is over-prioritizing low-value URLs, causing important pages to crawl late or infrequently. A balanced, updated scoring model is essential. Also, the crawler should gracefully handle malformed pages and malicious content that could crash parsers or extraction components. Isolation via the multi-stage pipeline assists here by quarantining and reporting errors without halting the entire crawl.

Engineer B

Regarding extensibility, while we focus on HTML and text now, the architecture should allow supporting new content types with minimal redesign. That suggests modular extraction stages that can plug in different parsers or renderers. For example, some pages require JavaScript rendering for meaningful extraction, which might be handled by separate specialized workers using headless browsers. This selective rendering is more resource-intensive and should be an optional tier.

Engineer A

That's forward-looking and wise. One open question is the initial seed URL selection strategy. Seeds could be supplied externally or derived by partitioning domains by geography, topic, or popularity. The choice affects coverage and freshness trade-offs. We might want experiments or heuristics to identify seeds that maximize coverage diversity and crawl yield, possibly pruning low-value or stale seeds over time.

Engineer B

Certainly an area for iterative improvement. Finally, observability will be critical. We should instrument each pipeline stage with metrics on throughput, error rates, concurrency, queue sizes, host response times, and policy compliance. Logs and alerting for anomalies will allow us to detect bottlenecks, failures, or politeness violations early. Only with robust operational visibility can the crawler scale reliably and respect web ecosystem norms.

Engineer A

In summary, our crawler design relies on BFS traversal with host-isolated queues enforcing politeness and a prioritized, layered URL frontier. We use a fault-tolerant multi-stage pipeline, cloud blob storage for data, hash-based de-duplication, and compliance with robots.txt. Open questions include seed selection, priority scoring refinements, dynamic content handling, and fine-tuning politeness delays at scale.

Engineer B

Right. Next steps could be prototyping the core frontier and worker orchestration logic, implementing priority scoring and politeness enforcement, and validating scalability with a moderate crawl. Parallel work on extraction modularity and storage integration can proceed based on initial feedback. Over time, we incorporate more sophisticated prioritization, fault tolerance, and legal compliance mechanisms.
