Designing a Scalable, Low-Latency, Health-Aware Load Balancer for Heterogeneous Backends

Two engineers collaboratively design a production HTTP load balancing system. They discuss trade-offs among common load balancing algorithms—including round robin, weighted round robin, least connections, and latency-aware methods—explore how to incorporate health checks and dynamic weighting, analyze failure scenarios, and consider observability and operational simplicity at scale.

Design challenge: Design a production load-balancing system that distributes traffic across backend instances while maintaining low latency, fairness, health-aware routing, graceful failure handling, and operational simplicity as the service scales.

Engineer A

Let's start shaping this load balancer design with our main goals: distributing HTTP requests across many backend servers, keeping overall latency low including tail latency, achieving fairness even when servers differ in capacity, and adapting in real time to server health changes. We also want to gracefully handle load spikes and failures and maintain simplicity as the system scales to thousands of servers.

Engineer B

Right. Our biggest challenges seem to stem from variable backend power and request costs, plus stale or noisy metrics. We need a design that uses real-time feedback for routing but balances complexity and operational overhead carefully. I think round robin or static weighted round robin are out, given they don’t adapt dynamically to health changes or workload variance.

Engineer A

I agree. Round robin is nice for uniform servers with similar request costs, but that’s rare in production. Weighted round robin improves by factoring in capacity differences, but manual weight tuning isn’t practical at large scales or for dynamic workloads. Plus weights can become stale as server health fluctuates.

Engineer B

So, shifting away from static weights, I’m inclined towards dynamic weighted round robin, where weights adapt from real-time latency metrics. But latency can be noisy or lagged, so it might not completely solve balancing outstanding request load specifically. That’s where least connections or least outstanding requests algorithms shine, dynamically routing to servers with fewer active requests to avoid overload.

Engineer A

Yes, least connections—or more precisely, least outstanding requests—seems like the strongest baseline. It dynamically balances by assigning new requests to servers with fewer current requests in-flight, which should naturally handle varying server capacities and variable request costs. Importantly, AWS recommends it when request complexity or capacity varies, while round robin suits uniform cases.

Engineer B

To add to that, incorporating health-aware routing is key. We'll need a health check subsystem that continuously probes servers and flags unhealthy ones, so the load balancer excludes or reduces routing to degraded backends. AWS and other mature systems treat health checks as a complementary safeguard to routing, not a substitute. So health determines eligibility; outstanding requests determine distribution among eligible servers.

Engineer A

Good point. This separation lets routing focus on balancing active load among healthy servers while health checks prevent routing to clearly faulty backends. But what about latency metrics? Should we add a latency bias into least connection routing? Something like a Peak Exponentially Weighted Moving Average—PEWMA—that prioritizes servers with lower smoothed latency metrics to improve p95 and p99 tail latency?

Engineer B

PEWMA is compelling but introduces complexity. We’d have to carefully tune parameters to avoid overreacting to transient spikes and prevent low-utilization servers starving higher-utilization but still healthy nodes. Also, continuous metric collection and smoothing add overhead and monitoring demands. Given the uncertainties in latency metric staleness and overhead, maybe it’s best to keep PEWMA as an optional, tunable add-on layered on top of least connections.

Engineer A

I’m with you. Let’s default to least outstanding requests with health-aware routing, and under high confidence in metrics and operational bandwidth, optionally augment routing weights with PEWMA or similar latency biases. This keeps the core simple yet adaptive enough to handle capacity diversity and real-time server health.

Engineer B

Agreed. Now, handling overloads and spikes is a failure mode we must mitigate. Since all backend queues can fill up, causing drops, we should include fallback behaviors, like retrying requests on alternate healthy servers or queueing at the load balancer level within limits before dropping.

Engineer A

Yes, retrying intelligently can improve success rates but raises concerns about head-of-line blocking and increasing latency. We need safeguards like limited retry counts, exponential backoff, and circuit breaker patterns. Also, for operational simplicity, retries should escalate only when initial routing findings deem the first choice unhealthy or overloaded.

Engineer B

Monitoring and observability tie directly into these behaviors. The balancer should emit metrics on request routing distribution, latency percentiles per server and backend group, retry rates, and dropped requests. Health check statuses and metric freshness should be observable as well to detect stale states or network issues affecting routing decisions.

Engineer A

Absolutely. Also, the load balancer’s internal state synchronization and scaling must keep pace with backend fleet size. We should design the metric collection pipeline for low overhead and timely aggregation to prevent stale information. Huge scale might push us toward distributed state architectures or eventual consistency with safety margins in routing decisions.

Engineer B

To summarize, our proposal is: first, continuously monitor backend health and exclude unhealthy servers; second, route requests using least outstanding requests among healthy backends to balance load dynamically; third, optionally integrate latency-smoothed weighting like PEWMA under conditions where metrics are reliable; fourth, implement limited retry and reroute paths before dropping requests; fifth, maintain comprehensive observability covering routing, health, load, and failures; and finally, architect for operational simplicity by keeping defaults straightforward and layering complexity only as needed.

Engineer A

One open question is tuning the parameters for the latency smoothing, retry limits, and health check intervals. These will depend on workload characteristics and backend variability. Our design should allow runtime configuration and gradual rollout of complexity to measure impact on latency and drop rates.

Engineer B

Another consideration is how the load balancer reacts if all backends become unhealthy or overloaded. An option might be fail-open routing or rate limiting at the front end to shed load early. We should also explore alerting thresholds tied to these states so operators can respond before SLA degradation.

Engineer A

Great points. To close the loop, what’s our next step? Should we prototype a least outstanding requests load balancer with health checks and basic retry routing, and then instrument to measure latency percentiles, retry success, and drop rates? We can iterate by adding dynamic latency weights and tuning parameters as measurable data comes in.

Engineer B

Yes, that sounds like a solid plan. Instrumentation will be vital to understand real-world metric staleness and routing effectiveness. From there, we can explore adding fallbacks, dynamic latency weighting, and investigate scaling techniques for state synchronization. Keeping operational simplicity in mind as we evolve is critical.
