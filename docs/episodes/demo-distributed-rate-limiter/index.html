Designing a Distributed Rate Limiter

Two colleagues compare a shared Redis counter with locally enforced token buckets, from consistency to failure recovery.

Design challenge: Protect an API with a distributed rate limiter while keeping latency low and avoiding a shared-service outage taking down requests.

Engineer A

We need rate limits across multiple gateways. A per-process counter won't work if traffic lands on different instances, so my first thought is a shared store like Redis.

Engineer B

A shared counter simplifies enforcement, but now every request may depend on Redis latency and availability. Before we commit, how strict do our limits need to be?

Engineer A

Let's say paid accounts require reasonably strict limits while anonymous traffic may tolerate small bursts. We should make that an explicit assumption, not present it as a known requirement.

Engineer B

Then we could try local token buckets for anonymous clients and a centralized counter for paid accounts. But consistency and failure handling still need careful testing.

Engineer A

For strict limits, an atomic Redis operation could update state and TTL together. It also gives us a place to collect rejects and saturation metrics.

Engineer B

And we need to ask what happens when Redis is unavailable. Do we fail open and risk overload, or fail closed and block paying customers? I'd prefer an explicit per-endpoint policy.

Engineer A

Agreed. Let's also test burst traffic, uneven gateway load and hot customer keys. That will tell us whether a single shard is adequate.

Engineer B

Our next step is a prototype and load test, not a premature final architecture. We can compare latency budgets, operational burden and the observed error rate.
